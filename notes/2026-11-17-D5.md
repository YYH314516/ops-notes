# D5 网络（2026-11-17）

今天四样：`ip` 看网络、`ss` 看端口、`curl -v` 看 HTTP、`tcpdump` 看三次握手。

## 0. 开场热身（重做 D4）

- `lsblk` 认盘：看 MOUNTPOINTS，`/boot`、`/` 落在哪块，哪块就是系统盘；剩下的是数据盘。
- `lvdata` 在 sdb1、sdb2 下面各出现一次，不是重复显示——说明这块 LV 由两个分区（两个 PV）拼成。
- `umount /data` 之后 `df -h /data` 显示的是 `/`（35G），因为 /data 摘下设备后只是根文件系统里的一个普通空目录，往回找最近的挂载点就找到 `/` 了。
  - **结论：df 看的不是"这个路径"，而是"这个路径落在哪个文件系统上"。**
  - 判断目录是不是独立挂载，`findmnt 路径` 比 df 直接。
- `mount -a` 按 `/etc/fstab` 把每一行挂一遍，所以知道 lvdata 该挂到 /data。

## 1. ip：看清自己这台机器

```bash
ip -4 a          # 看 IPv4 地址
ip route         # 路由表
ip route get IP  # 问"去这个地址系统会怎么走"
```

- `lo` 是回环接口，不是真网卡。发往 127.0.0.1 的包出不了网卡，直接绕回自己，供本机程序互相通信。
- `ens192` 是真实网卡，地址 192.168.158.101/24。`altname enp11s0` 是别名。
- **认网关**：路由表里开头 `default` 的那行，`via` 后面就是网关（192.168.158.2）。不是"排第一个"。
  - 同网段的目的地走 `192.168.158.0/24 dev ens192` 那行，不经过网关。
  - 跨网段的目的地走 default，交给网关转发。
- `ip route get 8.8.8.8` 输出 `via 192.168.158.2 dev ens192 src 192.168.158.101`：
  - `via` = 下一跳（交给谁），`dev` = 从哪块网卡出，`src` = 源地址（包里写"我是谁"），永远是本机地址。
  - 包交给网关后，如果网关做 NAT，源 IP 会被网关改成它自己再发出去——所以外网只知道 .2，不知道 .101。
- `ip route get 192.168.158.2` 没有 `via`，因为目的地就在本网段。
- `ip route get 127.0.0.1` → `local ... dev lo`，连网卡都不出。
- curl 报 `Network is unreachable` 就是"没有路由"：这台 VM 没有 IPv6 网关，v6 的 default 不存在。

## 2. ss：谁占了端口

```bash
ss -tunlp
```

- `-t` TCP，`-u` UDP，`-n` 显示数字不翻译名字，`-l` 只看 LISTEN，`-p` 显示进程名和 PID（要 root）
- 查"80 端口被谁占了"：`ss -tlnp | grep :80`，只有 `-p` 能告诉你"是谁"。netstat 已淘汰。
- 输出里 22 端口是 sshd（自己的 SSH 连接），888 是 chronyd（对时），后两个只监听 127.0.0.1 和 [::1]——只在本地，外面进不来。

## 3. curl -v：一次 HTTP 请求长什么样

`-v` = verbose，把连接过程和请求头、响应头全打出来。

```
* Trying ...              连接过程（DNS 解析 → TCP 连接 → IPv6 失败退到 IPv4）
> GET / HTTP/1.1          请求行：方法 路径 协议版本
> Host: example.com       我要访问哪个网站
> User-Agent: curl/7.76.1 我是谁
> Accept: */*             我什么类型都能收
>                         空行 = 请求头结束，后面是正文
< HTTP/1.1 200 OK         状态行
< Content-Type: ...       响应头
<                         空行之后才是正文
```

- **空行是硬规定**：头结束、正文开始的分界线。
- **Host 必须带**：一个 IP 上能挂几十个网站，靠 Host 区分你要哪个。`curl http://104.20.23.154` 和 `curl http://example.com` 打同一台机器，结果不同就是因为 Host。
- 状态码记三个：200 成功、404 不存在、301 永久搬家。
- 响应头 `Transfer-Encoding: chunked`：内容分块传，边生成边发。

## 4. tcpdump：亲眼看到三次握手

```bash
tcpdump -i lo -nn -c 20 'tcp port 8000'
```

- `-i lo` 抓哪块网卡，`-nn` 不翻译 IP 和端口，`-c 20` 抓 20 个包就停，单引号里是过滤表达式。
- `dropped privs to tcpdump` 是正常提示，抓完自动降权限。

**每行格式**：`发送方 > 接收方: Flags [状态]`

- 箭头方向就是包的方向，左发右收。
- `[S]` = SYN 请求连接，`[.]` = 纯 ACK 确认，`[S.]` = SYN+ACK，`[P.]` = 带数据的包，`[R]` = 拒绝，`[F]` = 结束。

**三次握手**（当打电话）：

```
① [S]   客户端 → 服务器   你：喂，在吗？
② [S.]  服务器 → 客户端   对方：在。我也要连你，你听得到吗？
③ [.]   客户端 → 服务器   你：听得到，开始说吧。
```

- 两个包各自证明什么：服务器**收到**你的 SYN（证明你能发），**回复**S​YN+ACK（证明它自己能收能发）；你的第三个 ACK 让服务器确认**你能收**。
- 为什么必须三次：两个方向，每个方向都要确认一次。2 次不够，服务器没法确认客户端能收。

**同一次连接里各阶段的样子**：

- 握手之后 `[P.] length 78` 就是 curl 里 `> GET ...` 那几行文本本身（同一件事的两个视角）。
- 响应分两段发（`chunked`）。
- 断开是 FIN：服务器先 `[F.]`，客户端把"确认你的 FIN"和"我也要断"塞进一个包发，所以四次挥手在这份抓包里只看到三个包，是正常的。
- tcpdump 从 SYN 之后自动切**相对序号**（1、79、156），不用算十位数加减。`ack` 永远比对方 `seq` 大 1（SYN 占一个序号）。

**抓不到正常握手的时候**：抓到 `[S]` 紧跟一个 `[R.]` 就是 RST——目标端口没有程序在 LISTEN，内核直接拒绝，也就是 `connection refused`。原因：`python3 -m http.server` 那个标签页关了，进程跟着死。起服务后先用 `ss -tlnp | grep 8000` 验证真的在 LISTEN 再抓。

## 4.5 深挖：seq/ack 数的是字节

- TCP 给**字节**编号，不是给包编号。一个包 `seq 1:79` = 带第 1~78 号字节（右端不含）。
- **ack = 我连续收到的最后一个字节 + 1**（即"下一个我想要的字节"）。
- SYN 和 FIN 不带数据，但**各占 1 个序号**。
- 一个包同时带两个号：`seq` 是自己的计数器，`ack` 是对面的计数器。用绝对编号（`tcpdump -S`）验算：
  - 下一个包的 seq 起点 = 上一个包的 seq 终点（不严丝合缝就是丢包或乱序）
  - ack 永远对得上对面上一包的 seq + length
- **累积确认**：客户端 `seq 1000:1200` 丢了、`seq 1200:1400` 到了，服务器仍回 `ack 1000`。ack 停在**洞的左边**，不是右边——宁可重传，也不让数据悄悄缺失。
  - 配套：SACK 选项能告诉对方"洞右边我也有"；连收 3 个重复 ACK 触发快重传。

## 4.6 深挖：标志位

| 旗子 | 含义 |
|---|---|
| SYN | 请求连接，带初始序号 |
| ACK | 确认（tcpdump 里末尾的 `.`） |
| FIN | 我这边的数据发完了（但不表示不收） |
| RST | 强制中断，不走挥手，在途数据作废 |
| PSH | 这段写完了，交给应用层，别攒（不是"紧急"） |
| URG | 紧急指针，基本废弃 |
| ECE/CWR | ECN 拥塞通知 |

- 三次握手的每个包都带 ACK 旗子（第二次是 SYN+ACK，一个包干两件事）。
- RST 三种来源：连没人在听的端口（内核代回）、对端程序 abort、防火墙 REJECT。

**三个报错的区别**：
- `Connection refused`：对方活着，端口没程序在听，**对方内核**回 RST
- `Connection reset by peer`：连上了，中途被**对端**掐断
- `Connection timed out`：包发出去没人回，通常防火墙静默丢包

## 4.7 深挖：窗口 / MSS / 拥塞控制

- `win` 是压缩显示的，真实值 = win × 2^wscale。本地连接 `wscale:4,7`，`win 512` 其实是 512×2⁷ = 64K。
- `wscale` 在握手时协商（options 里能看到）。14 位字段最大 65535，高速网络不够用才要缩放。
- **MSS**：一个包最多带多少 TCP 载荷。lo 是 65495，真实网卡 1460（MTU 1500 − IP 头 20 − TCP 头 20）。握手时协商，取双方较小值。
- **时间戳 TS val/ecr**：精确算 RTT + 防止序号回绕（PAWS）。
- 拥塞控制（Linux 默认 cubic）：慢启动（指数涨）→ 拥塞避免（线性涨）→ 快重传（3 重复 ACK）→ 快恢复（降一半）。**丢包 = 路堵信号，TCP 见到就降速。**

## 4.8 深挖：ss -ti 与 nstat 读什么

```bash
ss -ti state established    # 每条 TCP 连接的内核内部参数
nstat -az | grep -i retrans # 全系统累计计数器
watch -n1 'nstat TcpRetransSegs'   # 只看增量，运维的正确姿势
```

`ss -ti` 关键字段：
- `rtt:47.313/2.553` = 平滑平均 RTT / 抖动（毫秒）。交互式 SSH 的 rtt 被延迟确认拉高，看 `minrtt` 才准。
- `rto:248` = 重传超时；发包后多久没 ACK 就认为丢了，由 RTT 动态算（RTT + 4×抖动）。
- `cwnd:10` = 拥塞窗口，单位 MSS（1460×10 ≈ 14.6K）。初始窗口，慢启动刚起步。
- `app_limited` = 应用层没喂饱链路，交互连接常态。
- `retrans` 只在重传过时才出现。

判断 RTT：
- `minrtt` 本身就大 → 物理路径长（跨省跨洲）
- `minrtt` 小但 rtt 持续大 → 排队拥塞或延迟确认
- rtt 大 **且 retrans 在涨** → 真丢包，重点查

`nstat` 计数器（2026-11-17 实测）：`TcpRetransSegs 10`、`TCPSynRetrans 2`、`TCPFastRetrans 0`、`TCPLostRetransmit 7` —— 总数小、速率为 0，正常。SynRetrans 2 与当天 curl IPv6 不可达重试对得上；LostRetransmit 7/10 比例高但分母太小是噪声。

## 5. 面试常问

## 6. 今天卡住 / 出错的地方（错题本）

- **`umount` 后 `df -h /data` 显示 `/`**：以为 df 看路径，实际看路径落在哪个文件系统。
- **以为 fstab 是"开机自启的服务"**：fstab 是配置文件；`mount -a` 自己读它，systemd 开机也读它、生成 `data.mount` 单元。两路一个源头。
- **`tpc port 8000`** 少个 e 报 syntax error——看到 command not found / syntax error 先查拼写（D4 的 `fidisk` 同类）。
- **`python3 -m http.server` 的标签页关了**，进程没了，抓到的第一个握手变成 RST。
- 复述时把 `[S.]` 说成"多了个 ."，其实是"SYN + ACK 一个包干两件事"。
